# 客户端更新按版本号管理

## 本轮目标与边界

- 用户要求：后台以三段带上下箭头的数字输入版本号，游戏根据填写的版本判断更新；重新设计客户端更新页面，处理多余字段与不直观的操作。
- 用户确认：仅支持连接正式服的 1.1.0 及后续版本。已关闭旧服所用的更早客户端无需兼容。
- 基线：正式服部署记录为 `d4044fc7065636c451bd696fe85f8aef6df7ed72`；用户交付的正式包为 `1.1.0`，Android 构建号 `2026110101`。已安装的 1.1.0 尚未上传版本名称，使用经该包证实的构建号识别。
- 隔离工作树基于正式服提交，主工作区已有独立改动予以保留。本轮没有授权发布提醒、公告、邮件、奖励或补偿。

## 交互和业务决策

- 操作顺序：填写版本、选择玩家更新方式、填写玩家可见说明；维护计划只在选中维护时展示。三个版本分量使用 0 至 999 的整数，按各段数值比较。构建号及手工登录/运行构建门槛退出日常表单。
- 保留草稿、预览、发布确认、权限、审计、幂等、并发冲突、历史、再次提醒、撤回和维护开关。维护到开始时间后限制登录与业务；预计结束仅用于提示，必须手动结束。
- 仅提醒保留现有门槛；下次登录要求更新让当前合法在线会话继续并按既有短时重连规则处理；维护计划发布后向所有版本预告，维护结束后启用新版本登录和运行门槛。已有生效门槛不因本次改造降低。
- 尚未开始的维护计划可安全取消：停止该计划及其预告，不改变原有版本门槛或在线会话；已看过预告的玩家不会自动收到取消通知。维护时间统一使用并标注北京时间，发布确认对到期即维护保持明确提示。
- 已安装 1.1.0 用经过实包核验的构建号映射；后续客户端从自身清单读取版本，并在登录、状态和回执链路携带。不能识别的客户端不得伪装成已达到强制版本。
- 设计观察重点：桌面和窄屏先看到版本与更新后果；维护日期与维护模式放在一起；预览和确认能看懂真实影响。核对现有后台风格与亮暗主题。

## 验收口径

| 用户来源与触发条件 | 起点 → 终点 | 判定阈值及环境 | 覆盖范围 |
| --- | --- | --- | --- |
| 输入新版本并选择更新方式 | 输入三段数字 → 草稿保存与重读 | 只能保存三段 0–999 的完整整数，数值比较准确；本地隔离后台与服务 | 新建、编辑、预览、历史、权限、并发冲突及窄屏 |
| 发布仅提醒 | 管理员确认 → 客户端状态与实际展示判断 | 比目标低的版本提示，相同和更高版本不提示；1.10.0 高于 1.9.999 | 已安装 1.1.0 合同、新客户端、未知版本与提醒批次 |
| 发布下次登录更新 | 确认发布 → 新登录、在线业务与短时重连 | 旧版新登录被拦，已有合法在线会话和既定短时重连可继续 | 本地真实 HTTP/TCP、会话绑定及服务重启 |
| 维护更新 | 发布计划 → 维护开始 → 手动结束 | 维护期间所有版本受限；手动结束后低于目标版本受限；预计结束时间不自动开放 | 本地隔离管理接口、业务请求与状态查询 |
| 取消未开始的维护 | 发布未来计划 → 确认取消 → 状态重读 | 计划及预告关闭，既有版本门槛与在线会话保持；到期及维护中不能按未开始取消 | 本地隔离管理接口、重复请求、时点冲突与浏览器 |
| 跨时区安排维护 | 输入北京时间 → 保存 → 重读和确认 | 北京和纽约操作同一显示时间时得到相同实际时刻 | 不同时区的浏览器日期输入、预览、持久化与历史 |
| 版本策略安全 | 修改/撤回/重试 → 持久化与重读 | 不降低已有门槛；重复请求不重复操作；未知版本不绕过强制门槛 | 本地 SQLite、共享实例内项目专属 MySQL 测试库 |

以上为功能判定，无额外耗时上限。原机、发布与测试资源状态在完成后按实际记录。
