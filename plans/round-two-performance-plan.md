# 第二轮游戏并发与加载性能优化方案

状态：实施中。用户已授权先整理抽象规则，再按本方案优化；源码改动和验证证据记录在 `analysis/round-two-performance/`。尚未发布第二轮版本。

本轮目标是在现有 2 核 4 GB 服务器上，减少每次操作的重复读取、编解码和计算，继续拆除无关玩家之间的公共等待，并修复秘境及野外首领可能持续等待的路径。优先小改，保持原协议、资产原子提交、领奖幂等、冻结规则和冷恢复语义。

## 一、基线与范围

- 产品基线：前次核验的线上版本 `3fb495f`；研究文档提交 `5c4889a`。实施前重新核对实际线上版本及其他会话变更，以已发布代码为起点。
- 硬件范围：当前项目独占的 2 核 4 GB；沿用现有 MySQL。MongoDB、Redis、独立队列及新增数据库实例均不作为本轮前置。
- 数据范围：已覆盖 535 张生产表、2,241 个字段候选；已有编码证据的聚合字段 347 个，分布在 220 张表。全量候选包括普通文本、标识和未知格式，不能全部按 JSON 处理。
- 角色存档样本：73 个档案，`player` 平均约 467 字节，`game` 平均约 73.5 KiB，二者合计约 5.5 MB。主要问题是处理频率与重复工作，容量无需引入第二套数据库解决。
- 前次自然负载瞬时样本中，游戏约使用 1.67 核、MySQL 约 0.34 核。该样本说明需要重视 CPU 预算，不代表持续负载或容量上限。

当前版有界慢日志保留以下问题，时长为服务端 Dispatch，包含鉴权和业务处理，不包含全部客户端网络/资源加载：

| 场景 | 样本中的最大时长 | 本轮已确认的代码问题 |
| --- | ---: | --- |
| 竞技匹配 | 2,410 ms | 全局策略写锁、全名册读取和投影 |
| 竞技结算 | 8,135 ms | 计算期间持公共写锁，同一 P6 基础路径解码 5 次 |
| 夺宝单场 | 5,113 ms | 双方档案反复解码、重复准备和校验 |
| 夺宝扫荡 | 16,552 ms | 全真人候选锁、逐子战重复读取和同步计算 |
| 野外 Boss 开始 | 2,705 ms | 冻结和校验大输入期间仍持有关锁 |
| 野外 Boss 结束 | 5,405 ms | 输入验证、计算、刷新和结算集中在长链路 |

这些是慢日志中的最大样本，不是平均值、P95 或客户端总耗时；Boss opcode 也不能单独区分雪原与沙漠。秘境和客户端卡住仍需最短现场确定所属入口及第一处等待。

## 三、A：角色档案的小改方案

### A1. 同一事务内只加载、解码一次

当前 `p10LockProfiles` 为取得锁就完整读取、解码，调用方随后还会再次读取和投影；同一档案在夺宝子战中可重复处理多次。

- 对只需要取得角色锁、返回值未使用的调用，增加只选择主键的有序锁定入口，随后在实际使用处读取档案一次。需要完整对象的调用保留其业务数据返回。
- 已在同一事务锁定并解码的 `Profile/Player/GameState` 直接传给后续业务、投影和保存函数，减少再次按 ID 查询和解码。
- 复用范围限于该事务。回滚、重试和下一次请求重新读取；同事务内实际改动继续更新同一对象，不能复用写入前的旧快照。
- 多角色始终按 ID 升序取必要锁，保留各角色独立的持久化基线。

目标：每个参与角色的大档案首次解码一次；锁角色和读取业务数据的职责清楚。涉及双方资产的功能仍保持真实参与者之间的事务保护。

### A2. 鉴权和简单查询按需读取

- 鉴权读取角色/区服 ID、session、账号关联和撤权修订等必要字段；账号、客户端门槛及维护状态校验继续实时执行。
- 角色是否创建使用明确的存在性字段/查询结果，避免为判断非空拉取完整存档，也不伪造 `player/game` 字符串。
- 只需 `player` 中的小标量时不加载 `game`；需要库存、编队和玩法实例的入口再读取对应数据。
- 复用已经存在的 `scene_scope` 小投影做其覆盖范围内的路由。公会战、进行中副本等未覆盖分支保留原判定，不用空投影推断场景。

目标：鉴权和普通元数据查询不传输库存大字段；涉及资产或恢复的入口仍取最新所需状态。

### A3. 简化人物压缩编解码

当前压缩人物读取存在“解析 JSON→展开人物→重新编码整个 JSON→再解析”的中转；保存复用压缩块时又解压旧人物并编码当前人物比较。

- 在同一次解析中提取人物原始片段并读取其他字段，人物压缩数据只展开和验证一次。
- 在事务对象中复用已经验证的原文/压缩片段，减少保存时重复展开；人物实际变化仍按既有有界压缩器编码。
- 保持旧数组、压缩格式、摘要、数值精度、空值及既有兼容处理；客户端导出仍使用原协议形状。
- 只读路径按需处理人物；资产操作涉及人物时仍完整校验对应数据。

先减少重复转换，再考虑局部改动标记。本轮不为所有玩法引入一套通用脏字段框架。

### A4. 保留已经完成的保存优化

无变化不 UPDATE、仅写变化列和复用原压缩结果已经存在，继续保留。本轮进一步减少判断变化之前的 CPU 消耗。

`decodeProfileForUpdate` 中的资源恢复基线、背包版本和保存钩子有业务含义，不能直接删去中间编码。仅移除已被新对象/基线明确替代的重复工作。已经得到最终玩家快照的入口可以减少提交后的重复 `resourceProfile` 事务，但须验证恢复时钟和回包顺序；未证明等价的入口保留重读。

主要文件：[profileService.go](/Users/lirui/.codex/worktrees/hyjs-player-concurrency-20261102/hyjs/hyjs-server/service/profileService.go)、[profileStorage86.go](/Users/lirui/.codex/worktrees/hyjs-player-concurrency-20261102/hyjs/hyjs-server/model/profileStorage86.go)、[resourceRecoveryService.go](/Users/lirui/.codex/worktrees/hyjs-player-concurrency-20261102/hyjs/hyjs-server/service/resourceRecoveryService.go)、[gameService.go](/Users/lirui/.codex/worktrees/hyjs-player-concurrency-20261102/hyjs/hyjs-server/service/gameService.go)、[p10SocialService.go](/Users/lirui/.codex/worktrees/hyjs-player-concurrency-20261102/hyjs/hyjs-server/service/p10SocialService.go)。

## 四、B：战斗输入与规则的重复处理

### B1. 本轮先做请求内复用

- 同一请求、同一 P6 ID 与 input hash 的解压、反序列化和配置摘要验证完成一次后，向后续结算、奖励和排名事实传递已校验输入。
- 回执的归属、状态、扣费、终局和业务来源仍各自核对；复用输入不替代这些检查。可变状态变化后重新读取相应状态字段。
- 通用结算中的两次相同资格验证合为一次，向计算函数传递本次有效结果；继续执行一次完整原战斗计算。
- 同一请求的规则摘要、NPC 模板和已准备的双方属性按实际版本复用。
- 不跨事务复用可变角色，不引入全服角色缓存或公共计算排队锁。

目标：同一冻结 P6 输入每个请求验证/解码一次；多场扫荡的不同 P6 各自处理，规则和不变角色部分可复用。原操作记录、HP、胜负、随机结果和资产逐项保持。

### B2. 有依据后再复用不可变规则目录

批次 1 后若 Freeze/规则复制仍占主要成本，准备按当前已发布规则版本隔离的只读目录。当前目录在加载/发布时构建，读路径不逐战复制整表和计算相同摘要。

先核 normalizer、动态配置和引擎对表的写入；仍有写入的部分继续独立复制。角色、怪物实例、随机数和战斗过程始终独立。首批只复用当前运行所需目录，历史输入继续按需读取，不预热全部历史、不建立无界版本缓存。旧 input/configuration hash 和旧回放兼容保持。

主要文件：`battleReplayService.go`、`p6GenericMechanismService.go`、`p11GenericMechanismService.go`、`combatRoundService.go` 及调用它们的竞技/夺宝结算函数。规则与引擎行为不因优化改变。

## 五、C：竞技场

### C1. 查询不重建全服名册

- 将历史虚拟名次迁移、全名册修复和到期批量结算移出普通匹配/排行路径，沿现有维护流程有界完成；首次迁移完成后不在每次查询中重跑。
- 名次记录沿用现有 `p11_arena_members`。按当前榜归属、active 和名次范围筛选，查询只取需要的列；不加载全部成员后再内存挑选。
- 排行展示批量读取所需小资料，不生成每个玩家的完整战斗阵容。匹配只为最终少量候选准备当前阵容和冻结 match。
- 新达到资格的角色及已有档案迁移明确维护成员资格。本人真实等级变化沿现有角色保存入口处理；在批量迁移就绪前保留受控兼容路径，避免遗漏未主动打开竞技的合资格角色。
- 显示信息、候选资格和实际开战快照分别处理，不能把旧缓存阵容当作当前阵容。

### C2. 分离稳定配置与首次名次分配

`p11_arena_policies` 同时保存稳定参数和 `NextRank`，导致普通竞技也争用同一写入资源。本轮采用最小职责分离：

- 稳定配置：纯排行快照读取无需排他锁；接纳匹配/战斗时保留必要的共享规则租约。
- 初次排名分配：新增小表 `p11_arena_rank_allocators`，仅 `policy_id` 主键与 `next_rank`；本轮沿用当前榜/游戏库的作用域，不新增赛季或榜单产品概念。只有首次分配名次取该行写锁。
- 名次交换：沿现有 `position` 唯一约束，锁实际参与的成员行并按固定顺序更新；不通过写全局配置保护所有战斗。
- 虚拟对手尚无真实成员行时，提交前复核目标名次占用，继续由 `position` 唯一约束裁决同一名次的并发争夺。被抢先占用时整笔回滚并返回原刷新要求，不重复扣费；不为所有虚拟位置新增公共写门。验证两人争同一虚拟名次与争不同虚拟名次两种情况。
- 新入榜读取已提交的资格投影，仅按分配器→新成员的固定次序写名次，不锁其他角色的资产档案；匹配和开战继续核当前资格。既有战斗按有序参与角色→必要策略租约→有序成员及回执处理，所有交叉入口一并核锁序。

迁移在停止新名次分配的窗口，先按现有虚拟位/历史证据规则核定有效 NextRank，再初始化分配器。已有真实名次、首达奖励和虚拟身份保持。运行后若回到旧程序，先停止新分配，将有效计数同步回旧字段并核唯一性，再切程序，避免旧计数重复使用。

### C3. 结算保留资产原子性

先移除公共写锁、重复准备和重复 P6 处理，缩短原事务。第一批保留既有受理、扣费与回执提交边界，不同时引入持久化多阶段战斗状态机。

写锁限定实际资产和名次参与方；若防守者仅提供冻结阵容，进一步核查其整档写锁是否必要。需要缩短共享资源持锁时间时，先用冻结快照和版本复核证明等价；只有实测仍有必要，才单独设计锁外计算，不能改变后台停用/截止对已受理战斗的合同。

主要文件：`p11ArenaService.go`、`p11ArenaNPCService.go`、`p11ArenaFightService.go`、`p11ArenaDailyService.go`、`p11ArenaPrizeService.go`、`p11ArenaRankRewardService.go` 和相关模型/结构 SQL。

## 六、D：夺宝与扫荡

- 列表先做便宜的资格过滤，免战/黑名单等批量读取；最终候选再生成战斗投影。保留原扫描与未知候选限制，避免因漏查直接生成 NPC。
- 同一事务内复用本人、候选、阵容、规则及子战结果，移除每个真人子战双方各多次完整解码的重复链路。
- 扫荡先发现实际参与集合，按 ID 排序取锁；锁后复核资格和资产。若需要更换参与者，整笔回滚、重新发现并按序取锁，不持锁追加顺序更小的角色。
- 不再为没有参与本批次的候选长期持锁。仍实际涉及多人的批次按真实参与集合保护。
- 保持 1/5 次、能量不足、目标已获得、持有者耗尽、掉落随机、真实碎片转移和整批回执语义。子战独立提交不纳入默认实现，避免改变中途失败的回滚行为。

若首批后候选扫描仍为主要成本，再增加按“角色＋碎片”归属的小型持有者投影及区服/碎片查询索引。该投影作为二级索引，原资产仍为权威；必须覆盖所有增减入口、同事务维护并完成回填核对后启用，不能只靠提交前复核弥补漏候选。未证明必要前不新增这张投影表。

主要文件：`p11PlunderService.go`、`p11PlunderFightService.go`、`p11PlunderSweepService.go`、`p11PlunderNPC84Service.go`。

## 七、E：雪原、沙漠 Boss 与场景互斥

### E1. 普通 Boss 查询与写入分开

现有 `shared_field_boss55` 已按区服、场景、线路、位置建主键，继续复用。

- 投影和查询使用非锁定快照，不对本线所有 Boss 逐个 UPDATE 锁。
- 首次创建、到期换代、提交伤害或唯一击杀，才锁具体 Boss 主键；锁后复核 UUID/代次和当前 HP。
- 规则准备、输入编解码和战斗计算不持有无关 Boss 的锁。
- 共享扣血、实际贡献、唯一击杀、奖励和同代幂等继续在必要事务中提交。

### E2. 沙漠首领减少锁内准备

沙漠已按线路保存事件。本轮复用现有事件和冻结输入，重点减少开始阶段对大规则反复冻结/校验、结束阶段重复处理输入的成本。任何规则准备移位都要复核事件 ID、线路、版本和接纳时刻；已接纳战斗继续按其原快照履约。

### E3. 场景成员互斥收至房间

当前普通移动共享读，但进入、退出、换线仍持进程级场景排他门。

- 在当前单游戏进程架构内，将容量/成员变化的短排他范围收至既有 owner、区服、场景、线路；源/目标房间按固定顺序处理。
- 移动继续按本人顺序处理，不写线路容量分配资源；不同场景/线路的成员变化互不等待。
- 广播取所需快照后释放成员保护，沿现有会话鉴权和单连接队列发送，网络写入不在公共排他区间。
- 不增加分布式锁服务或第二套场景状态表。扩展多进程不属于本轮范围。

主要文件：`sharedFieldBoss55Service.go`、`sharedFieldBossLines85Service.go`、`fieldBossService.go`、`ggoBossBattleService.go`、`p10SceneService.go`。

### F2. 服务端目录与加载准备

秘境状态目录按小列和批量个人状态读取；不需要消费或恢复写入的查询不持角色排他锁。确需到期恢复的路径单独保留必要事务。觉醒章节/怪物配置按当前版本复用，入场和碰怪避免重复准备相同规则与角色来源。

### F3. 等待结束必须有明确去向

- 沙漠 15 秒超时后，复用已有 active/receipt/恢复接口确认是否已接纳：已接纳则续接同一冻结战斗；确认未接纳才释放本次等待并允许重试。
- 晚到响应按原实例、会话和场景归属处理，不影响之后的新入战。单纯隐藏蒙层或清标志不算恢复完成。
- 觉醒等待按开始响应、网络错误、资源失败和结束回执分别处理，清理对应等待并提供原界面中的恢复操作。
- 始终沿用原游戏加载动画、组件和交互。预显示动画只改善首个反馈，不代替真实开始/完整战斗加载提速。

主要文件：`dailyCopyService.go`、`p7AwakeService.go`、`tools/desert_extraction/FieldRuntime.cs`、`FieldBoss.cs`、`BattleRecovery.cs`、`ColdBattleRecovery.cs`、`tools/client_field_settlement/LocalFieldSettlement.cs`，以及按原 IL 确定的精确 hook。原战斗引擎规则和协议不变。

## 九、G：表设计与对象存储的后续边界

本轮首批不全面拆 `profiles`，也不把所有 JSON 转成另一种编码。相同主体、总是一起读取的小状态保持聚合；独立高频更新、点查/排序/索引及冷热边界有实际收益时才拆。

| 项目 | 本轮决策 |
| --- | --- |
| 竞技排名分配器 | 为分离真实写热点的最小结构调整，随 C2 迁移和回退一起交付 |
| 夺宝碎片候选投影 | 条件项，首批对比证明候选扫描仍占主要成本后实施 |
| 角色位置/线路/loading 独立运行状态 | 条件项；若小改后普通位置请求仍主要耗在大 game，单独拆此高频边界，资产维持原格式 |
| 通用字段表、通用快照巨表 | 不纳入方案；保留明确业务归属和查询约束 |
| 活跃 player/game 搬对象存储 | 不纳入主方案；资产事务继续在 MySQL |
| 不可变规则版本包、已结束大回放外置 | 独立试点，主优化不等待它完成 |
| MongoDB | 当前 2 核 4 GB 不新增第二套业务数据库 |

对象存储试点须先取得厂商、地域、内网 endpoint、存储级别和额度信息，再由服务器做少量有界 GET/PUT 对照。对象不直接暴露手机；上传在资产锁外完成，验证后才登记引用，中断可恢复。保留紧凑业务证明与所有消费者的验证能力，不能把仍供扫荡、领奖、称号或续局使用的大记录直接按 24 小时删除。

单次请求最多 3 个 JOIN，关联信息批量读取；不以增加查询次数换取表数量下降。稳定配置和实际分配计数、角色资产和历史证明分别按读写边界处理。

## 十、验收标准

### 10.1 正确性与互斥范围：必须满足

1. A 的战斗或个人事务被有意保持时，B 的无关个人操作能在 A 释放前完成；验证使用真实 InnoDB。不同竞技参与者、不同公会/队伍、不同线路/矿点和不同 Boss 位置分组验证。
2. 同角色、同资产、实际双方转移、同矿点占用及同 Boss 代次保持必要约束。币/钻/能量/碎片守恒，失败回滚、同 stamp 重放、唯一击杀和领奖不重复。
3. 后台停用、截止、规则发布与已接纳事实的关系保持；新请求不借用旧已停规则，历史已接纳快照仍可履约。
4. 档案、规则和输入复用不跨入不兼容事务/角色；回滚后丢弃内存结果。旧存档、旧压缩输入、重启、断线和冷回执均可读取与验证。
5. 普通匹配不扫描/重建全服档案；纯 Boss 投影不对本线全部 Boss 取写锁；同一请求不反复解码相同 P6。必要的业务事实校验继续存在。
6. 客户端超时、失败和晚到响应均有可恢复终点，不永久挡住下一操作，不重启已接纳战斗来重抽结果。

### 10.2 建议性能目标：实施时固定输入后评估

以下是本方案提出的优化目标，尚未成为用户已验收硬指标，也未声称已经达到。服务端以请求进入 Dispatch 至返回计时；客户端另记发包/回包和页面可用时间。

| 代表场景 | 服务端建议 P95 目标 |
| --- | ---: |
| 普通个人信息查询、移动处理 | ≤200 ms |
| 秘境状态目录 | ≤300 ms |
| 竞技匹配、排行 | ≤500 ms |
| 竞技/夺宝单场结果处理 | ≤1,500 ms |
| 夺宝 5 次扫荡汇总 | ≤5,000 ms |
| 野外 Boss 开始 | ≤500 ms |
| 野外 Boss 结束 | ≤1,500 ms |

对比条件固定原阵容、seed、规则、资产、对手和次数，覆盖单请求及 2～4 个不同角色的小并发，并记录 SQL/事务数、档案/P6 解码次数、大字段字节量、CPU/分配及锁等待。样本不足时报告逐次耗时和最大值，不从慢日志推算 P95，不以瞬时 CPU 下降推算容量提升。复杂阵容超过目标时保留原样本和目标，按真实引擎、等待和 I/O 占比分解，不换简单阵容冒充通过。

客户端常用查询以“点击→页面数据可用”1 秒为建议目标。沙漠继续沿用已接受的硬性起止：碰撞确认→第一帧原加载动画 ≤1 秒；采集有效触发→动作和倒计时启动 ≤1 秒。房间、资源、HUD 和战斗原动画各自计时，冷/热加载分开，不用提前显示蒙层掩盖服务器等待。

### 10.3 验证与实机控制

- 复用前一轮 53 项的适用基线；按本轮影响补档案/codec、并发、幂等、截止、冷恢复检查，合批执行真实 MySQL。SQLite 只补兼容与纯逻辑，不能替代 InnoDB 锁验证。
- 通用存档/战斗核心变更合批跑相关包及一次有界联合回归，执行编译、vet、构建。历史全套仍有基线失败、缺失证据和超时限制时列差异，不放宽断言、不把 SKIP 计为通过。
- 实机只覆盖有客户端改动或首个故障的新范围：代表秘境入口、对应雪原/沙漠 Boss 正常链、一个失败/晚回包恢复。客户端先合批构建一次；新的实机失败以新事实决定增量修复。
- 消耗、领奖和战斗结算测试使用隔离环境；生产核验版本、健康及不改变资产的入口，必要时观察自然请求。未经单独授权，不在生产测试发奖、发公告或群发邮件。
- 复用共享本机服务和项目隔离库，数据库回归/压测串行，不创建新 MySQL/Redis 实例。
