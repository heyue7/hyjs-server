# 优先复用 GM 合理业务的执行方法

适用于用户提供的 `黑衣剑士-离线联机-GM版.apk.1`。原制品及已保留的 REA 方法证据见 [调查入口](../../../analysis/gm-apk-resource-audit-20261017/README.md)；[副本](../../../analysis/gm-apk-resource-audit-20261017/planning/dungeons.md)、[养成](../../../analysis/gm-apk-resource-audit-20261017/planning/growth.md)已经完成的定位直接复用。

1. 按 [07 执行计划](../../../plans/07-gm-reference-execution.md)选一个完整业务结果，例如主线开关卡→战斗→进度→掉落→后续成长。先查现有 Go 与已验记录，留下真实缺口清单，已有能力继续沿用。
2. 从现有 GM 索引找到对应请求与处理方法，一次读取完成该业务所需的状态、条件、扣费、奖励、返回和保存代码。方法来源与 APK/DLL SHA 记一次；无需重新逆向全包或重复证明不变来源。
3. GM 已实现且合理、符合当前目标的流程直接作为实施依据，沿其业务顺序翻译到现有 Go 域。主线关卡、解锁进度、波次选择和奖励组织优先采用；有明确现有契约冲突时只调整冲突部分并记原因，避免先重新设计整条链。
4. 将 C# 本地内存、UI 回调和文件保存接入现有原协议、MySQL 事务、持久 run/回执及个人日历。保留我方已经具备的归属、幂等、并发、冷恢复和多波次能力；不搬其云端地址、账号凭据或玩家存档，不另造旁路账本。
5. GM 的服务端状态规则可在已授权范围内采用，注明来源与差异；运营奖品、价格、次数与周期沿项目skill的四类决定，未知项交用户配置，不因GM已有商店代码恢复自设廉价供应。未知服务端机制按自建机制表登记。固定胜负、空方法、明确 unsupported 和与原表冲突的简化单独排除，不能当完整实现，也不据此阻塞其他合理代码的复用。
6. 每个单元完成差量实现及必要静态/领域验证后合入批次；同一候选集中构建，手机与数据库按实际影响合批验收。不因每搬一个方法就单独跑完整回归。实际出现的逻辑/资源缺项才定向补查；觉醒入口不恢复已撤销的资源预检。
7. 交付只记新增玩家行为、采用的方法、修改原因和实际验证范围；已移植、已集成、已发布、原机通过分开。结束本批后按用户授权决定下一单元，暂停要求不触发自动续跑。
